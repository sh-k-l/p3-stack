### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.**

1. **Run the owner loop unchanged.** GitHub CLI (`gh`) is the forge. Never require Graphite (`gt`). One delegated worker per PR owns its change end to end: build, first push, a ready PR opened before self-proof, self-proof (gates, CI, receipts), skeptical review-bot triage, a slop-strip, a comment pass (`agents/comment-sicko.md`), and babysit to green per `playbooks/babysit.md`. Spawn each owner with `delegate_task`, `mode: "async"`, and the role line for its kind of work from `p3-models.md`. Every brief stands alone: the worker gets only the brief, never your context. Owners parallelize when the work is self-contained; give each its own worktree with `delegate_task` and `isolation: "worktree"`, one writer per worktree. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens the PR ready, never draft. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners keep `children.tsv` with one row per child task. Record its task ID, role, branch, head SHA, state, and result. Use `delegate_task` with `isolation: "worktree"` for a child that needs a separate checkout. Use a fresh delegate for each round. Carry the full brief and all unresolved findings forward.
2. **Audit on a real loop.** The root runs an audit tick every hour. On the operator's go, the root arms `schedule_task` with `{"type":"interval","everyMs":3600000}` and a prompt that runs this tick. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk and audit the operation against it. Fix drift during that tick. Probe each owner with `task_status` or `t3_thread_read`. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that passes its expected runtime without a side effect as stuck. `task_cancel` it and dispatch a replacement at once. Do not wait for a polite return. Collect each decision trail. End the tick only when no delegated work remains. On the operator's stop, cancel all child tasks and delete the scheduled tick.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. At each code-ready SHA, the root starts independent `delegate_task` verifiers per **swarm** and reads their results with `task_status`. Re-run the required gates at that SHA. Verify the changed behavior on the real app or command. Use `preview_*` for a browser and `device_*` for a simulator. Run the same scenario on trunk. If trunk lacks the feature, record that fact and verify the new behavior and its final result. Use at least two diff review tasks with the full brief. Give each a separate focus, such as behavior, races, or data safety. A clean verdict needs the live check. Send every proven finding to a fresh owner in one fix round. Require a red test for each behavior defect, or a reproduction record when a test cannot show it. Include the defect in the next review brief. Each changed patch needs a fresh verdict. Reuse a result only under the patch-id rule in `playbooks/shipping.md`. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified. Call `link_pull_request` for the PR the moment it joins the stack.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, push with `--force-with-lease` only after an `ls-remote` check, and set the PR base to the parent branch. Create it with `gh pr create --base <parent-branch>`. Retarget an existing PR with `gh pr edit <pr> --base <parent-branch>`. Only the root PR targets trunk. Never submit or register the chain through `gt`. `list_thread_pull_requests` returns the stack bottom to top; check it against the intended order after every append.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch-id is unchanged. A new increase to a pinned gate or budget needs the root's approval after verifier proof. The root may approve only within the operator's grant and the tool's approval contract. Record the approval and its evidence. A verifier checks that record. Never bypass an approval that the service enforces. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up on GitHub, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready. Arm `watch_pull_request` on the stack root, end the turn, and triage on wake.

Use this playbook when the operator wants a reviewed stack before landing. For independent changes with separate landing instructions, use **figure-it-out**.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
